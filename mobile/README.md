# Guardian Mobile

The monitored person's app: React Native (bare CLI) + TypeScript, talking to
`../server`.

This is the device that gets watched, so it is the device that has to be
trustworthy. Every design decision below follows from that.

## Setup

The Gradle and Xcode scaffolding is generated by React Native's own CLI, which
refuses to run in a directory that already has source in it. `bootstrap`
generates it in a scratch directory and merges it underneath these files -
existing files are never overwritten - then applies three patches the
generator cannot know about.

```bash
npm run bootstrap     # generates + merges native scaffolding, patches config
npm install
cd ios && pod install && cd ..    # macOS only
npm run android                   # or: npm run ios
```

Point the app at your backend with `GUARDIAN_API_URL` (see `.env.example`).
The Android emulator reaches your machine at `10.0.2.2`, not `localhost` -
`src/config.ts` already defaults to that.

Checks: `npm test`, `npm run typecheck`, `npm run lint`.

## What the four pieces do

**Pairing** (`src/screens/PairingScreen.tsx`) redeems the guardian's 8-character
code by PIN entry or QR scan. Redeeming only moves the connection to `PENDING`;
the guardian confirms on their side before anything is shared. The screen
states in plain language what is being agreed to, including that the
connection can be ended unilaterally - a consent screen that buries what it
grants is not consent, and this is where that is decided.

**Privacy control** (`src/screens/PrivacyControlScreen.tsx`) is ordered by what
someone reaches for when anxious: kill switch at the top, per-channel switches
below it, SOS docked at the bottom of every screen. Guardian-locked channels
render as locked-on with the reason and a visible route to ending the
connection, rather than as a switch that mysteriously refuses to move.

**Indicator + foreground service** - see the honesty section below.

**SOS** (`src/components/SosButton.tsx`) is never disabled by privacy state.
The backend accepts SOS with the shield up because that is exactly when it
matters; a local guard here would silently undo that. It requires a confirm
tap, because a panic button that fires in a pocket trains people to ignore it.

## The server is authoritative

The app's toggles are optimistic for responsiveness, but
`server/src/domain/privacy.ts` decides. When a `privacy:state` event arrives it
overwrites local state outright, including a change still in flight. **A toggle
springing back is correct behaviour** and is deliberately left visible instead
of being re-applied.

`src/realtime/socket.ts` also re-checks each `command:sensor` against local
state even though the server already gated it. Cheap, and it means a
compromised or simply buggy server still cannot start a stream the user has
switched off.

## Honesty about the indicator

The blueprint asked for an "unhideable" indicator. Three layers exist, and they
are not equally strong - worth being precise, because the marketing claim
should match what the code can actually promise:

| Layer | Strength |
|---|---|
| OS camera/mic indicator | **The real guarantee.** A modified build cannot remove it. |
| Foreground service notification | Persistent, but since Android 13 a user *can* swipe it away (the service keeps running). |
| In-app red banner | Ours, so a modified build could remove it. |

So the honest claim is "the operating system shows when the camera or
microphone is on, and we add our own disclosure on top" - not "we render an
indicator that cannot be hidden".

Two consequences enforced in code:

- `AndroidManifest.xml` deliberately does **not** request `SYSTEM_ALERT_WINDOW`.
  An overlay permission is how an app draws over the OS indicators, and the
  comment there says so, so nobody adds it later for a "floating widget".
- `ios/InfoPlistAdditions.md` deliberately omits the `audio` background mode.
  It would allow background microphone capture without call-style treatment,
  which is the covert capture this product exists to prevent. Microphone
  check-ins are foreground-only on iOS - a product decision, not a limitation
  to route around later.

`src/native/ForegroundService.ts` and `GuardianServiceModule.kt` expose no
method to hide the notification or suppress the indicators. That absence is
the design.

## Structure

```
src/
  api/          client (single-flight token refresh), endpoints, wire types
  store/        Redux Toolkit slices + reconcile.ts (pure, tested)
  realtime/     socket.ts, indicatorSync.ts
  native/       ForegroundService bridge (no-ops on iOS by design)
  screens/      SignIn, Pairing, PrivacyControl
  components/   StreamIndicatorBanner, PrivacyToggle, MasterShieldCard, SosButton
  pairingCode.ts, location.ts, config.ts, theme.ts
android/app/src/main/java/com/guardianmobile/service/*.kt
```

Pure logic is kept out of components on purpose - `reconcile.ts` and
`pairingCode.ts` hold the rules and are tested with no simulator, no database
and no network, the same split the backend uses.

Accessibility is wired throughout rather than retrofitted: switches carry
`accessibilityRole="switch"` with real `checked`/`disabled` state, the
indicator banner is an assertive live region so a screen-reader user gets the
same disclosure a sighted one does, and touch targets are >= 48dp.

## Not built yet

- **Media capture.** `onSensorCommand` in `App.tsx` raises the indicator, tells
  the server, then stops after 15s. The WebRTC/LiveKit attachment point is
  marked `TODO(media)`. The indicator path is exercised end to end; no media
  is sent. Keep the ordering when you wire it: indicator up *before* capture
  starts.
- **Sign-out UI.** The action exists in `authSlice`; nothing dispatches it yet.
- **Background location on iOS** beyond the `location` background mode.
- **Push notifications** for SOS delivery when the socket is down.
